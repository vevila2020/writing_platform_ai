# 系统流 / 签到流 / 模拟器流

这张卡只补题材差异。通用结构、场景、人物判断仍按 `novel-craft`。

## 读者承诺

读者要的是**看得见的成长反馈**：规则清楚、奖励可预期、选择有代价，主角靠系统放大自己的判断。

- 核心快感：完成条件 → 获得奖励 → 能力变化 → 解决更大的问题。
- 系统是工具，不是主角：它发布规则，但不替主角做决定。
- 作者要先回答：系统为什么选中他？系统的限制是什么？没有系统他还剩什么？

## 核心循环

```text
系统给出目标或触发条件（任务、签到点、模拟机会）
→ 主角评估风险与收益，选择做或不做
→ 执行中遇到现实阻碍（对手、时间、资源、道德）
→ 结算（奖励、惩罚、新信息、新限制）
→ 能力或处境改变，引出下一个目标
```

数值和规则要能让读者记住：不要每章新增一堆设定。

## 开篇（前三章）

1. **第一章**：让系统在具体困境里出现，并给出第一次可见收益。读者要立刻明白"系统能做什么、要什么"。
2. **第二章**：展示系统的限制或代价（任务失败惩罚、使用次数、暴露风险），避免变成无脑外挂。
3. **第三章**：让主角用系统奖励解决一个现实问题，同时引来更大的注意或敌意。
4. 开篇避免：面板说明一大段、主角瞬间无敌、系统替主角解释一切。

## 系统设计

至少写清：

| 项目 | 问题 |
| --- | --- |
| 触发 | 系统什么时候出现、什么时候给任务 |
| 目标 | 任务要求是什么、怎样算完成 |
| 奖励 | 给什么、多久能用、有没有上限 |
| 惩罚 | 失败怎样、能不能拒绝 |
| 限制 | 次数、冷却、使用条件、暴露风险 |
| 成长 | 升级路径是什么、下一阶段解锁什么 |
| 来源 | 系统是谁做的、为什么存在（可以晚揭示，但要提前埋） |

- 面板只展示必要信息，不要每章贴完整属性。
- 奖励要匹配难度，避免通胀。
- 签到流要有"地点/时间/条件"的变化，不能每天机械打卡。
- 模拟器流要让"模拟"和"现实"产生差异与代价。

## 爽点与钩子

- 优先用"条件达成 + 奖励兑现"型爽点：读者能预期，又会有惊喜。
- 奖励最好解决当前困境，同时打开新问题。
- 章尾钩子常用：新任务出现、惩罚倒计时、系统异常、他人察觉、隐藏条件触发。
- 主角的主动性要比系统更强：是他选择怎么用，而不是被任务牵着走。

## 人物与关系

- 系统不能抢戏，主角的决策、性格、关系才是故事核心。
- 同伴要知道主角"有秘密"，制造信任与试探。
- 对手要有办法对抗系统优势：情报、规则、资源、人多。
- 系统的来源与目的要埋线，不能永远只是工具。

## 常见失效

- 系统万能，主角没有任何真实困难。
- 面板数据堆砌，读者记不住也不再关心。
- 任务机械重复：签到 → 奖励 → 打脸。
- 奖励通胀，前期珍贵后期廉价。
- 系统人格化过度，变成话痨旁白。
- 主角失去主动性，完全被任务驱动。
- 从不解释系统来源，也不埋任何线索。

## 动笔前确认

1. 这一章系统给了什么目标或条件？读者清楚规则吗？
2. 主角为什么选择做或不做？风险是什么？
3. 奖励解决了什么问题，又打开什么问题？
4. 数值/能力变化是否可感知、可比较？
5. 系统之外，主角自己的判断和关系有没有推进？
